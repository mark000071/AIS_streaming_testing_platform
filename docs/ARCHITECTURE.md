# Architecture: combining 呈现端 (presentation) and 模型端 (model)

## Goal

Demonstrate MCM-Net's live-deployment result — the served rule (motion-mode
router + learned scorer, backed by MCM-Net candidates) beating
Constant-Velocity and Kalman baselines on real AIS traffic — through a map
UI, without merging or forking the model repository. Two repositories, one
demo:

```
┌───────────────────────────────┐        file/DB contract        ┌──────────────────────────────────────┐
│   MCM_streaming  (模型端)      │  (docs/DATA_CONTRACT.md)       │  AIS_streaming_testing_platform (呈现端)│
│                                │ ──────────────────────────────▶ │                                        │
│  serving/aisstream/            │  predictions/*.parquet + queue │  backend/app/data_source.py           │
│    predict/server.py           │  metrics/metrics.sqlite         │    (reads only, stdlib json+sqlite3)  │
│    reconcile/scoring.py        │                                 │  backend/app/main.py  (FastAPI)       │
│    metrics/aggregate.py        │                                 │  frontend/  (Leaflet map, vanilla JS) │
└───────────────────────────────┘                                 └──────────────────────────────────────┘
        unmodified, this PR                                              all new code lives here
        never touches this repo
```

This repository is a **consumer**, not a fork: it is programmed directly
against the JSON/SQLite shapes `MCM_streaming/serving/` already produces
(see `docs/DATA_CONTRACT.md`), so pointing it at a real, running
`MCM_streaming` serving deployment is a config change (`AIS_MODEL_DATA_DIR`),
not a code change. `MCM_streaming` is never edited, vendored, or imported
from this repo — the PR chain for this work stays entirely on
`AIS_streaming_testing_platform`.

## Two data modes, one codebase

| | `demo` | `bridge` |
|---|---|---|
| Data source | `demo/data/*.json` (bundled, generated by `demo/generate_demo_data.py`) | `MCM_streaming/serving/runtime/{predictions/*.parquet,queue/predictions,metrics/metrics.sqlite}` |
| Requires GPU/torch/weights? | No | No — this service never runs inference itself; it only reads what the model-side `predict` worker already wrote |
| Requires a live AIS feed? | No | No — works equally well against a **replayed** archive (`aisstream.replay`, see `MCM_streaming/serving/README.md`) as a live one |
| Purpose | Demonstrate the UI/UX and the "served beats baselines" story anywhere, offline, deterministically | Show the real, currently-deployed numbers |

Mode is selected by `AIS_DATA_MODE` (`demo`/`bridge`), or auto-detected: if
`AIS_MODEL_DATA_DIR` exists and is non-empty, `bridge`; otherwise `demo`.
See `backend/app/config.py`.

## Why this boundary, and not e.g. a shared Python package

- **The model side is CPU/GPU- and Python-version-constrained** (py3.7,
  torch 1.7.1+cu110 for training-parity inference; see
  `MCM_streaming/serving/README.md`). The presentation side should be free
  to run modern Python/FastAPI without fighting that constraint. A file/DB
  boundary means the two processes never share an interpreter or
  dependency set.
- **The task instructions for this work require the model repository to
  stay untouched** and all commits/PRs to land on
  `AIS_streaming_testing_platform`. A read-only consumer of an existing,
  already-documented output format is the only design that satisfies that
  without duplicating MCM-Net's serving code here.
- **Presentation code should survive model-side refactors.** As long as
  `predict/server.py`'s JSON shape and the `scores` table schema stay
  stable (both are treated as a versioned contract on the model side, per
  its own `HARDENING_TODO.md`), this repo doesn't need to change when the
  model, scorer, or router are retrained or swapped.

## Request flow (bridge mode, deployed)

1. `MCM_streaming/serving` runs its seven supervised processes
   (`ingest → tracker → gate → features → predict → reconcile → metrics`)
   exactly as documented in its own README — unchanged by this work.
2. `predict/server.py` writes one JSON file per forecast to
   `runtime/queue/predictions/`; the collector moves it into
   `runtime/predictions/YYYY-MM-DD.parquet` within one main-loop tick.
3. `reconcile` + `metrics/aggregate.py` write ADE/FDE-scored rows into
   `runtime/metrics/metrics.sqlite` ~10 minutes later.
4. This repo's `backend/app/data_source.py::Store` (bridge mode) reads the
   latest forecast per vessel from (2), parquet first, for the live map and reads (3) for the metrics panel, on every
   `/api/reload` call or process restart.
5. `frontend/static/app.js` polls the FastAPI endpoints in
   `backend/app/main.py` and renders vessels, candidate fans, and the
   served-vs-baseline deltas on a Leaflet map.

## Request flow (demo mode, this PR's default)

Same steps 4–5, except step 1–3 are replaced by
`demo/generate_demo_data.py` → `backend/app/demo_data.py`, a deterministic
synthetic-but-schema-accurate dataset (see its module docstring for exactly
what it fakes and why) so the demo runs anywhere with just Python — no
GPU, no weights, no live feed, no dependency on `MCM_streaming` being
checked out at all.
